# 문서화 컨벤션

## 1. 문서 종류와 위치
| 종류 | 위치 | 목적 |
|---|---|---|
| 코드 주석 | 소스 파일 안 (`///` XML 주석) | 클래스와 공개 메서드의 계약 설명 |
| 시스템(기술) 문서 | `Docs/Systems/제목.md` | 한 기능의 구조, 흐름, 사용법 |
| 설계 결정 기록 | `Docs/Decisions/제목.md` | 왜 이렇게 만들었는지 |
- 문서의 제목은 영어로 문서의 정체성을 최대한 간단히 명사 형태(문장형은 피함)로 적는다.
- 만들어진 문서의 제목은 바로 사용하지 않고 그렇게 정한 이유를 설명 후 사용 허가를 받는다.

## 2. 공통 규칙
- 언어는 한국어, 코드 식별자는 원문 그대로 쓴다.
- 문서 한 개는 한 화면 분량(약 100줄 이내)을 목표로 하고, 넘으면 쪼갠다.
- 확인되지 않은 내용은 `(미확인)`으로 표시한다. 추측을 사실처럼 쓰지 않는다.
- 날짜는 `YYYY-MM-DD`로 쓴다.

## 3. 시스템 문서 형식
1. **개요**: 이 시스템이 해결하는 문제 (2~3문장)
2. **구성 요소**: 클래스/오브젝트와 각자의 책임
3. **동작 흐름**: 순서가 있으면 번호 목록이나 mermaid 다이어그램
4. **데이터 구조**: 주요 필드와 의미
5. **사용 방법**: 씬에서 설정하는 법 (인스펙터 항목 포함)
6. **제약과 주의점**
7. **관련 문서**: 링크

## 4. 설계 결정 기록 형식
- **상태**: 제안 / 채택 / 폐기
- **배경**: 어떤 문제가 있었는지
- **검토한 선택지**: 장단점 포함
- **결정**: 무엇을 골랐고 왜 골랐는지
- **결과**: 이 결정으로 생기는 제약과 후속 작업

## 5. 갱신 규칙
- 클래스의 공개 인터페이스를 바꾸면 해당 시스템 문서를 같은 작업에서 고친다.
- 구조를 바꾸거나 방식을 뒤집으면 설계 결정 기록을 새로 추가한다. 기존 기록은 지우지 않고 상태만 `폐기`로 바꾼다.

## 7. Claude에게 문서를 시킬 때
- 코드를 보지 않고 문서를 쓰지 않는다. 필요한 파일이 없으면 먼저 요청한다.
- 문서 초안을 쓸 때 코드에 없는 기능을 만들어 내지 않는다.
- 문서와 코드가 어긋나 있으면 어긋난 부분을 먼저 알려 준다.
